第二集只看一个动作：文件从编辑器到 commit，中间经过哪里？如果 git add 只是添加文件，后面就会很奇怪。

先把 Git 项目看成三层。Working Tree 是正在编辑的文件；Index 保存下一次准备提交的内容；Repository 保存已经提交的历史。后面所有命令，都只是让内容在这三层之间移动。

当你修改 app.js，变化先只在 Working Tree。Git 看见它变了，但 Index 和 Repository 都还没动。modified 的意思，就是还没进入下一次提交。

执行 git add app.js。Git 把当前这一刻的 app.js 放进 Index。注意，是这一份内容，不是永远自动同步这个文件。所以 add 更像选择内容，加入下一次 commit。

如果 add 之后又继续编辑，Working Tree 会变成新版本，Index 里仍然是刚才 add 的旧版本。同一个文件就会同时有 staged 和 unstaged 的变化。要提交新版本，需要重新 add。

执行 git commit 时，Git 读取的是 Index，不是编辑器里最新那份 Working Tree。它把 Index 里的内容形成快照，写入 Repository。这里的新提交 C1 保存的是 v1，工作区的 v2 还没有进去。

所以记住这条线：Working Tree 负责修改，Index 负责选择，Repository 负责记录。下一集，我们拆开 commit，看它里面到底是什么。
